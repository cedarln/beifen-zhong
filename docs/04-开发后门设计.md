# 开发后门与跳过等待设计 v0.1

目的说清楚：**让人能在不等 22 小时的前提下把整条剧情走完、并判断每段戏是不是真的成立**。这跟玩家可得的"快速模式"是两件事，必须分层，否则我们最后会做出一个"玩家能跳、我们不能跳"或者反过来的东西。

剧本层面**零额外成本**：结构文档第七节已强制每个 `wait` 节点必须带 `first_line_after_wait` 和快速模式摘要，后门只是消费这些字段。任何缺 `first_line_after_wait` 的等待，自检脚本直接判 fail——这条已经生效，后门不会踩到无摘要可显示的空洞。

---

## 一、两层开关

| 层 | 谁能看到 | 能力 | 存档影响 |
|---|---|---|---|
| 玩家层 · 快速模式 | 通关一次后自动解锁 | 等待压成文字摘要，可跳 W1–W7 全部（**W5-2 除外，不可跳**） | 打 `quick=true`，结局《备份》的前置条件之一 |
| 开发层 · 后门面板 | 连点标题栏 5 次 + 输入 `307` | 下面第二节全部能力 | 每次进入会话写 `debug_used`，导出时可见 |

**发布包默认隐藏开发层面板。** 面板入口常驻但不显示：`BuildConfig.DEBUG` 为 false 时，需要 `307` 口令；正式包的口令由远端配置下发，我们内测时自己知道，玩家侧没有可搜索的入口。理由不是怕人发现，是怕**玩家误用后门跳掉等待之后，得出"这游戏没什么体验"的错误结论**——那会污染我们收到的每一条反馈。

## 二、后门面板八项能力

1. **时间倍率** — 1× / 60× / 3600× / 自定义。这是最主力的用法：3600× 下 22 小时等待 = 22 秒。倍率作用在**时钟层**而不是逐个节点打补丁（见第三节），所以等待、每日衰减、周年触发全部一致加速，不会出现"跳过了等待但 D5 还认为只过了一天"的假象。
2. **跳章** — 直接进 D1–D7 任一章首。跳章时按第六节度量预算表**注入该章应有的起始三度量**，否则 needs 条件会全线不满足、剧情走不动。面板上明确显示"已为你注入 trust=66/awareness=58/integrity=72（D5 起点）"，让我们知道自己是"走进去的"还是"掉进去的"。
3. **按 node id 传送** — 输入 `d5_n540` 直接落位；同时支持"传送到上一个 choice"和"传送到本章峰值节点（◆）"，后者按结构文档节点图里的标记取。
4. **度量实时读写** — trust / awareness / integrity 三个滑杆，实时生效，用于验证第六节预算表的可达性（例如：把 awareness 拉到 70–76、integrity ≥38、三封信读完、不开快速模式、不当共犯 → 检查隐藏结局《紧急联系人》是否真的可达）。**可达性检查必须靠这个做，不能靠读代码推。**
   （2026-10-27 第一版实现后更新：阈值以 `script/act7.json` 的 `d7_e760.requires_all` 为准，原文的 62–68 / ≥55 与定稿不符，docs/02 同步改正；这条可达性现在由 `PlaythroughTest` 逐条跑，不再靠手滑。）
5. **伪造 signal** — 手动触发白名单里的任意 signal，用来测 D4 的低电量、D3 的凌晨窗口、D5 的灭屏三十分钟而你真的不用锁屏、以及"你的设备日期是 2024-10-31"这种我们平时测不到的分支。伪造时在气泡上打一个 `DBG` 角标，避免我们误以为它自然触发了。
6. **结局直达** — 七个结局一键跑，含失败与假结局。每个结局直达按钮旁显示"自然达成需要的前置条件"，让我们能对比"设计意图"与"实际演出"是否一致。
7. **强停 / 崩溃模拟** — 直接 kill 进程，验证 `post_exit_notification` 与闹钟恢复后不重复投递、不丢消息。**这一项是安卓侧最容易出事的地方**（Doze + 进程被杀后 WorkManager 延迟可达 15 分钟到数小时），必须有按钮才能测。实现时这一格配了三个按钮：`现在强停`、`打开/关掉快速模式`、`清投递台账（N）`，台账条目直接列在下面（见第 4.5 节）。
8. **失真日志（硬约束）** — 所有被后门跳过或加速的等待，在面板与导出 JSON 里标红，记录 `skipped_ms` 与 `accelerated_by`。顶部常驻一行：`本局跳过 27h14m，其中 W1-4 / W2-2 / W5-1 未完整体验`。

最后一条是我要守的原则：**后门允许我们不作弊地评估。** 一个从没等过 22 小时的人没有资格判断 D6 那段的节奏对不对。日志存在的意义就是每次我们想下结论时先看见自己跳过了多少。W5-2（灭屏 30 分钟）是唯一在玩家层不可跳、但在开发层允许强制跳的节点——跳了就在面板上写明"此处体验已失真"。

## 三、时钟层：为什么倍率不能做成"直接结算"

最省事的做法是给每个 wait 加一个"立即完成"按钮。我们不做，因为那会让**度量随真实时间衰减**这条线断裂——而它正是本作最重要的道德压力：玩家拖着不玩，她就会提前散架（integrity 每天 -3）。

正确做法：剧本里所有等待只声明 `duration_ms`，引擎唯一信任的是 `GameClock`：

```
gameTime = (System.currentTimeMillis() - installTime) * RATE + OFFSET
```

倍率改 `RATE`，跳章改 `OFFSET`，伪造一天就是 OFFSET += 86_400_000×N。于是等待、每日衰减、"每年 10 月 31 日 20:14"的周年触发、"凌晨 1–4 点窗口"全部走同一个时钟，加速 3600× 时窗口判定也不会假。唯一例外：`night_window` 需要区分"游戏时钟"与"设备时钟"，面板加一个 `夜间窗口按设备时钟判定` 的开关（默认开）——否则 3600× 下每章都会路过凌晨，D3 的深夜节点会廉价地天天触发。

## 四、安卓侧的兑现要点（写给第一版引擎）

- 全本地调度：`WorkManager`（可延迟，只用于兜底补投）+ `AlarmManager.setExactAndAllowWhileIdle`（真正按时送达）+ 一次 `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` 引导。**不用 FCM**：没有服务器，也不该有——她"只存在你手机上"这件事是设定的一部分。
- 首次启动的授权引导必须由剧本承担（圣经映射表里的 `exact_alarm_granted` 那句"你给了我一个能叫醒你的权利"）。技术引导和叙事合成一句话，别做成两段割裂的弹窗。
- 22 小时等待跨 Doze / 跨重启：保存 `dueAt` 到磁盘，`BOOT_COMPLETED` 与 app 冷启动都做一次 `catchUp()`（把逾期消息按顺序投递，最多合并成一条"这几条是我在你不在的时候想说的"）。**逾期不补投 = 玩家以为游戏坏了。**
- 省电模式下 exact alarm 可能被拒：`canScheduleExactAlarm()` 为 false 时降级为 `Window` 触发 + 冷启动 `catchUp()`，并在面板上标红"当前设备无法精确唤醒"，别让玩家看到"她没来找我"当成 bug 投诉。
- `screen_off` / `background_gt_90s` 用 Lifecycle + `ACTION_SCREEN_OFF` 接收器实现即可，不需要任何敏感权限。这条守住了圣经的隐私红线。

### 4.5 第一版落地的唤醒链路（2026-10-27，写完并跑过单测的实际形状）

原设计只写了"闹钟 + 兜底补投"两句话，真做下去发现落点选错会同时踩三个坑，所以定成现在这样：

```
ReminderScheduler.schedule(ref, text)
  ├─ AlarmManager.setExactAndAllowWhileIdle → WakeReceiver（exported=false）
  │     └─ WakeGate.worthPosting(存档, ref, 设备时刻, 游戏时刻) → post() + DeliveryLedger 记账
  └─ WorkManager(CatchUpWorker，exact 可用时延后 5 分钟) → 同一条 WakeGate + 同一张台账
```

三条约定都有代价，也都各自挡掉一个真实事故：

1. **闹钟的落点是 `BroadcastReceiver`，不是 Activity。** 到点的是通知，不是"把应用拽到前台"。
   早期版本用 `getActivity`，于是 `post_exit_notification` 那条（d1_n150『我数到六十了』，60 秒）
   因为 ref 以 `post-` 开头被 Activity 直接 `return`，正文谁也没投，"按时"变成"5 分钟后兜底送来"。
2. **发不发由存档判，不由调度器内存判**（`WakeGate`，纯函数，10 条单测覆盖）。三道闸：
   这条等待还在不在档上（玩家点开过／后门跳走 → 已清空，闭嘴，这就是"没有幽灵通知"）；
   游戏时钟是否真的走到 `wait_until`（Doze 提前唤醒 → **提前说话比不说话更假**，闭嘴）；
   补投那条有没有 arm 过（被 `only_if` 挡掉的待办根本不该存在，闭嘴）。
   判据读档不读内存，所以进程被杀、设备重启之后仍然成立。
3. **去重记在设备侧的 `DeliveryLedger`（SharedPreferences），而且键是 token 不是 ref**：
   `ref@wait_until` / `ref@armed_at`。按 ref 记账会把二周目（通关后开快速模式重走 D1）的同一条
   等待永久消音——那是比复读更难查的错。它不进存档：发没发是设备事实，不是剧情事实。
   面板第⑦项因此多了一个按钮「清投递台账」：**不清台账强停重开，她绝不重说（＝不重复投递）；
   清了再重开，她必须再说一次（＝不丢消息）**——两句话都能当场验，不用等 22 小时。

另外两处第一版的明确取舍：`LOCKED_BOOT_COMPLETED` 从接收器过滤器里删掉了——它要求 directBootAware + 设备加密存储，
而存档在凭据加密区，留着只会得到一个永远不来的承诺；`USE_EXACT_ALARM` 也从清单里删了——它一声明就无条件生效，
D1 那句"你给了我一个能叫醒你的权利"会当场变成假动作（代码里必须真的可能被拒绝），而且商店政策只放行时钟/日历类 App 用它。

**2026-10-27 真机（模拟器）跑出来的两处修正**，都记在这里，因为它们推翻了上面写过的话：

1. **"闹钟还在不在"不能问系统，要自己记账**（新增 `ScheduledAlarms`）。
   上一版用 `PendingIntent.getBroadcast(FLAG_NO_CREATE)` 探系统表，把"有凭条"当成"有闹钟"。
   模拟器上 `pm clear` 之后当场复现了反面：PendingIntentRecord 还留在表里，AlarmManager 的闹钟已经没了，
   于是 `armWait` 与 `CatchUpWorker` 双双认为"已经排过了"，谁都不补排——她的话从此没有人负责。
   现在 `schedule()` 自己记 `ref → 触发时刻|开机标记`（开机标记 = `now - elapsedRealtime`，
   重启或改系统时间都会让它变掉，账自动作废），`hasPendingAlarm` 读这本账。
2. **长等待没到点时 `CatchUpWorker` 现在会补排一次**（前提是没有活的排程）。
   原来那句"22 小时＝264 次空转"的顾虑是对的，但结论下反了：真正的原因是**无条件**重排会自我喂养；
   加上第 1 条那本账之后，补排一次就收敛（第二次跑看见账上有同一个触发点，直接返回）。
   不补排的代价是重启即失约——22 小时这一觉玩家是会把手机关屏的。
   同一本账还兜住了周年那条：《紧急联系人》承诺的"每年 10 月 31 日 20:14"在重启后由 worker 照存档补排，
   否则那句承诺只在"玩家一年不重启"的年份里成立。

还有一条不属于后门但属于这条链路：**夜间静默窗口 23:30–07:30**（`QuietHours`，详见 docs/02 第五节）。
`schedule()` 把落进夜里的唤醒点推到次日 07:30，投递侧（`WakeReceiver` / `CatchUpWorker`）再兜一次底。
模拟器实测（设备时间改到 02:00，D1 那个 2 分钟等待）：`dumpsys alarm` 里那条唤醒的 `origWhen` 是
`2026-10-28 07:30:01`，通知栏 0 条，而玩家盯着屏幕时等待照常在 02:02 结算——**推后的只是通知，不是她那边的时间**。

## 五、给剧本作者的副作用提醒

后门让"跳等待"变得太容易，于是写剧本时会有个隐蔽的诱惑：**既然能跳，就再多塞一个 4 小时等待。** 不许。每章的等待总量已经锁死在结构文档第一节那张表里，自检脚本会按章校验 `sum(duration_ms)` 是否超出预算 ±10%。这条约束存在的唯一理由是保护没有后门的那批玩家。

## 六、验收标准（第一版必须做到这五点）

1. 3600× 倍率下，从 D1 装好到 D7 任一结局，全程可在 25 分钟内跑完，且中途无需碰 adb。
2. 跳章入口的度量注入与预算表逐字一致（面板显示的数字能被自检脚本复算）。
3. 任何被跳过的等待，在导出 JSON 里都有对应标红记录；导出的 JSON 能重现这一局的全部 choices。
4. 强停与重启之后不重复投递、不丢消息，`catchUp()` 在逾期 3 天的场景下按合并规则生效。
5. 正式包里 `307` 面板不可通过 UI 猜出来（连点标题栏无提示），且 `debug_used` 不会污染玩家存档——我们的内测反馈数据要能和真实玩家数据分开。
