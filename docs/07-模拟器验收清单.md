# 模拟器验收清单 v0.1

> 这份文档只有一个用途：**把"我们真的在设备上看过它跑"和"我们推理它应该能跑"分开**。
> 发布前每一条都要有出处——命令、看到的输出、或者明确写"没验"。
> 复盘时最贵的教训都是这一类：`docs/04` 里那条"有凭条 ≠ 有闹钟"就是推理性判断骗了我们，
> 直到在模拟器上按了一次灭屏才发现所有等待都不再重挂。

## 一、环境

| 项 | 值 |
|---|---|
| AVD | `beifen34`（Pixel 6 · android-34 · google_apis · arm64-v8a，headless 启动） |
| 宿主 | macOS，JDK 21，Android SDK 35，构建一律 `--offline` |
| 时区 | Asia/Shanghai（静默窗口的判据是**设备本地时间**，换时区会改变行为） |
| 装包 | `adb install -r -g <apk>`；release 包名 `cn.linan.backingup`，debug 包名多 `.debug` |
| 造夜间 | `adb root` → `settings put global auto_time 0` → `date 10280200.2026`（把设备拨到凌晨两点） |
| 造白天 | 同上，`date 10281000.2026` |

仪表三件套，验收全靠它们：

```bash
adb -s emulator-5554 shell dumpsys alarm | grep -F backingup   # 闹钟到底挂没挂、几点触发（一定要 -F，见第五节第 2 条）
adb -s emulator-5554 shell dumpsys notification --noredact     # 通知是否真投递、走哪个渠道
adb -s emulator-5554 shell uiautomator dump /sdcard/w.xml      # 屏幕上到底是什么字
```

造降级（验第二节第 5 条）：

```bash
adb shell appops get  cn.linan.backingup SCHEDULE_EXACT_ALARM   # 这台 AVD 上默认就是 deny，别去改它
adb shell appops set  cn.linan.backingup SCHEDULE_EXACT_ALARM deny
adb shell pm grant    cn.linan.backingup android.permission.POST_NOTIFICATIONS  # 只想验"敲门"这一步时才给
adb shell pm clear    cn.linan.backingup                        # 从 D1 开头重走（会清存档，只在模拟器上做）
```

通知权限没给时 `dumpsys notification --noredact` 里本包是 `importance=NONE`——
这不是渠道被改了，是 13+ 的运行时权限还没批，投出去也是静默丢弃。

屏幕上的文案不要靠肉眼看，用 `tools/smoke_tap.py --dump` 打出来，`--tap "文案"` 点下去。

## 三、长等待跨重启（`tools/device_wait_reboot_check.py --reboot`）

跑法：`push_to_wait()` 用 uiautomator 把界面推到屏上出现「还要等」——**这一步是整个验证的前提**，
没有 in-flight 等待就去 reboot，看到的"重启后 0 条闹钟"是正确答案但什么都证明不了
（我们连着两次栽在这儿，脚本现在会直接判"这条验证作废"）。
推到等待后：抓在途闹钟 → `adb reboot` → 轮询 `sys.boot_completed=1` → 再等 45 秒
（`BOOT_COMPLETED` 广播 → `BootReceiver` → `catchUp()` 重挂）→ 对比两边的**唤醒时刻 `origWhen`**，
不看条数（条数会被已经烧掉的那条短等待污染，上一版就是这样把一次真 PASS 读成"没重挂"）→
回前台读屏 + crash 缓冲。

v0.1.0 发布前这次跑通的是 release 包（`pm clear` 之后走到 `d1_w100`，2 小时等待）：

```
重启前在途唤醒点 1793143800000            ← 2026-10-28 07:30:00.000
重启后     同一条：RTC_WAKEUP #26 origWhen=2026-10-28 07:30:00.000
                     window=+1h0m0s0ms flags=0x20
                     maxWhenElapsed=+9h21m19s667ms
boot_completed=1；crash 缓冲里本包 0 行（唯一一条 SIGTRAP 是系统的 searchbox 进程）
屏幕回到：「她那边：她决定去走廊尽头看看…」/「还要等 1小时56分」
```

这条 07:30 而不是 01:02，是因为 2 小时等待的落点掉进静默窗口，`QuietHours.clamp` 把**唤醒点本身**
推到了早上——顺带把第二节第 6、7 条（推后通知、不动游戏时钟）在真实链路上又验了一遍。
前台那条路是独立的：`d1_w100` 到点(01:02)时玩家如果正盯着屏幕，1 秒一跳的倒计时会直接结算，
不依赖这条被推后的闹钟；两条都到点时由 `DeliveryLedger` 去重（`WakeGateTest` 10 条单测）。

**结论：PASS。** 这是本项目**唯一"玩家看不见但一定会碰到"**的路径：手机重启是日常事件，
而重启之后如果她不再来找你，玩家看到的现象叫"游戏坏了"。

`tools/device_reboot_check.sh` 保留作手工全流程版（它多做了"关通知栏、读渠道、再冷启动"几步，
但它会先 `am force-stop` —— force-stop 会连带清掉本包闹钟，所以**它不适合做这一条**，
只适合重启后看"没在途等待时应用还能正常起"）。

## 四、没验的（v0.1.0 发布时如实列出）

1. **真机**。全部结论来自 arm64 模拟器。不同 ROM 的后台管控（各家"自启动/省电策略"）
   能把 `SCHEDULE_EXACT_ALARM` 之外的链路掐掉，这部分我们没有任何数据。
2. **真的 7 天**。单章最长 33 小时的等待没有连续真跑过：跨天推进靠 `GameClock` + 单测里的
   时间注入，加上模拟器改系统时间。中间如果玩家把系统时间改了/关了自动时间，她那边会发生什么，
   只推理过，没玩过。
3. **一周年**。`YearlyTrigger` 的锚点是 10-31 20:14，跨到下一年的那条只在单测里造过日期；
   模拟器只拨到"第二天凌晨"，没有拨到"明年"。
4. **音频的现场听感**。装载、循环点、增益读数都被验证过，但"在真实扬声器上够不够像一栋楼"
   这件事只有耳朵能判。
5. **6 秒人声节点**（`voice_2014.m4a`，D5 选『先别开』后在 D7 出现）与**后台 90 秒静音**
   （docs/06 红线 2）没有做过现场播放验证。
6. **无障碍/大字模式**。文本密度按手机气泡设计，放大字体下的排版没看过。
7. **卸载后重装之外的数据路径**：`allowBackup=false` 意味着换机就没了——这是设计，
   但"换机党"的实际体验我们没有走过一遍。

第 4、5 两条是下一版最该补的：它们不需要新代码，需要的是一个人戴上耳机玩一遍。

## 五、四条"验过但只验到一次"的坑（写给下一次改这块代码的人）

1. **`SCHEDULE_EXACT_ALARM` 在模拟器上是 deny**。这台 AVD 的 appops 默认拒绝精确唤醒，
   `ReminderScheduler.schedule()` 的旧写法在这种情况下**一条 AlarmManager 闹钟都不挂**，
   只剩 WorkManager 那条延迟 Job——而长延迟 Job 在 Doze 里可以被推到几小时之后，
   她说的"晚上九点"就变成"不知道哪天"。现在多了 `setAndAllowWhileIdle` 那条降级分支（第二节第 5 条）。
   附带一条剧情级的收获：剧本里 `d1_n140` 那个"你给了我一个能叫醒你的权利"的授权**真的是可被拒的**，
   不是表演——所以那句台词不是假动作。
   做这一条时**不要**用 `appops set … allow` 去"修"它，那是把要验的东西关掉。
2. **`am force-stop` 会连带清掉本包闹钟**（第二节第 14 条现场量到：在途等待时强停 → 闹钟 1 → 0）。
   所以"重启补投"这一条不能先 force-stop（`device_reboot_check.sh` 的第 1 步就是为别的目的写的，
   用它跑这一条会得到假阴性）。而"强停之后她就再没来过"这个 bug 是真玩家会撞的：
   设置里那个"强制停止"按钮、以及覆盖安装更新，都会走到这条路。
   修法是冷启动先把自己记的账销掉一次（`GameViewModel.init` → `ScheduledAlarms.forget`）；
   账本防的是"玩家每点一下屏幕都重排一次"，不是"这次开机不许重排"。
   **还有一条仪表本身的坑**：`adb shell "dumpsys alarm | grep 'walarm*:pkg'"` 里的 `*`
   会被远端当成正则量词（"walarm" + 零个或多个 "r"），于是一律匹配不到、输出 0 条——
   我差点把这条当成"链路坏了"的结论写进文档。查闹钟一律用 `grep -F`，或者像脚本里那样先取整行再比。
3. **设置页那两行状态（通知开关 / 精确唤醒）只在冷启动读一次真值**。
   玩家停留在界面时去系统设置改开关，这里不会当场变——要重开一次 App。
   不做成实时轮询是有意的：`recordGrant()` 记的是剧情里她那一次的所得，
   每 60 秒重读设备会把"她在剧情里问过你"这件事覆盖掉。
4. **Android 15 的贴边（edge-to-edge）是强制的，而我们的模拟器看不见它**。
   v0.1.0 发到真机上，用户第一句话是"界面的最上面和最下面分别和通知栏、虚拟键盘重合了，
   导致按钮按不到"——D1 那三个选项里的第三个正好压在导航条上，等于第一章开局就卡死。
   根因：`targetSdk 35` 起系统忽略 `android:statusBarColor` / `navigationBarColor`，
   内容一律铺满整块屏幕，让位要 App 自己做；而我们没做。
   **为什么 14 条验收全过却没抓到它**：AVD 是 android-34，那一版还不是强制贴边，
   而我们也没有主动调 `setDecorFitsSystemWindows(false)`，于是系统替我们让了位——
   模拟器上"看起来是对的"，恰恰是因为它在替我们掩盖问题。
   修法是两处：`MainActivity` 显式进入贴边（这样 API 34 也能当场复现这条），
   三个全屏根容器（`GameScreen` / `SettingsSheet` / `BackdoorPanel`）加 `safeDrawingPadding()`。
   两个写的时候踩过的细节：
   ① `safeDrawing` 是 `systemBars ∪ displayCutout ∪ ime` 的**并集**，
      所以一条 `safeDrawingPadding()` 同时管住状态栏、刘海、虚拟键和键盘，底部不会叠出两段空白；
   ② 在**可滚动**的两页里，这条 padding 必须写在 `verticalScroll()` **之前**。
      写成 `verticalScroll().safeDrawingPadding()` 也能"看起来正常"，但那是把让位塞进了滚动内容里——
      一往下滚，第一行就滑到状态栏底下了。让位属于视口，不属于内容。
   弹窗（口令框、挂断确认）用的是独立 Window，系统仍在替它让位，实测键盘弹起时整块上移，没动它。
   这条的教训不是"忘了加一行 padding"，是**我们的验收环境比发布环境宽松**：
   以后凡是"屏幕上点得到点不到"这类结论，只有真机算数；模拟器能验的是链路、时间、日志。
