# 发布与命名规范 v0.1

> 写给"下一个游戏"的自己。第一版能跑之后，仓库、版本号、APK 文件名、签名密钥这些
> 琐碎东西如果没有约定，第二款游戏开始就会变成一团糊——而 APK 的名字是唯一一个
> 玩家会替我们记住的东西（"我下载的是哪个包？"）。

## 一、仓库划分：一款游戏一个仓库

不做"游戏合集仓库"。理由不是洁癖：

1. **签名密钥必须一游戏一把**。Android 用签名判断"能不能覆盖升级"，两把钥匙共用一把，
   等于把两款产品的升级通道绑死在一起——第一款出问题要换密钥时，第二款陪葬。
2. **剧本是内容资产，不是代码依赖**。《正在备份》的真相在 `script/*.json`，
   它挂进 assets 的方式（`assets.srcDir(file("../../script"))`）是本作特有的，
   下一款未必用同一套引擎。
3. **Release 页要干净**。玩家下载时看到 8 个 APK、3 个游戏名，会下错。

| 项 | 约定 | 本作取值 |
|---|---|---|
| 仓库名 | 游戏标题拼音 slug，kebab-case | `beifen-zhong` |
| GitHub 可见性 | 默认 private，公开前先看第二节 | public（2026-10-28 转公开，第二节的三条已逐条过） |
| `applicationId` | `cn.linan.<短名>` | `cn.linan.backingup`（debug 包加 `.debug` 后缀） |
| 工程目录 | 仓库根放 `android/ script/ docs/ tools/` | 同 |

## 二、公开之前先确认三件事

1. 存档与转写导出里没有任何真实用户数据（本作导出的是剧本生成的文本，成立）。
2. `docs/` 里没有写进真实地址、真实姓名、真实手机号（本作 D1 的"紧急联系人"是虚构号码）。
3. 密钥、口令、后门密码不算秘密（后门口令 `307` 写在代码里，是**开发层**的门，
   不是安全边界），但 keystore 与它的口令**必须**在仓库外。
4. **提交作者身份**。公开仓库的 `git log` 是给人看的：机器名、真实姓名、私人邮箱都会跟着出去。
   本仓库统一 `cedarln <cedarln@users.noreply.github.com>`；v0.1.1 之前有一条提交带的是
   `linan@My-MacBook-Air.local`，转公开前用 `--amend --author` 改掉了（未推送的提交，改它不丢东西）。
   转公开前跑一遍：`git log --format="%an <%ae>" | sort -u` 和
   `git grep -nI -E "linan@|/Users/|1[3-9][0-9]{9}"`（后者会误报时间戳和 sha，看清楚再下结论）。
5. **公开即剧透**。`script/*.json` 与 `docs/05 全篇对话实录` 是七章全文和七个结局，
   转公开等于把结局摆在门口。这是 2026-10-28 玩家侧需要一个能下载的公开仓库时做的取舍，
   下一款如果要留悬念，就得走"代码私有 + APK 放公开渠道"那条。

## 三、版本号与 tag

- `versionName`：语义化 `MAJOR.MINOR.PATCH`。第一版可玩 = `0.1.0`；
  剧本改一句 = PATCH；加一章或加一条结局线 = MINOR；重做成正式发行 = `1.0.0`。
- `versionCode`：**只增不减**，每个发布包 +1。Android 只认它判断覆盖安装，
  装过 5 再装 4 会被系统拒绝，玩家看到的是"安装失败"，不是"版本旧了"。
- Git tag：`v<versionName>`（一个仓库一款游戏，不需要前缀）。
  若哪天真要把两款塞进一个仓库，tag 必须改成 `<slug>-v<version>`——git tag 不允许 `/`，
  所以别指望 `beifen-zhong/v0.1.0`。
- Release 标题：`<游戏名> v<version>`，正文按第四节的三段式写。

## 四、APK 产物命名

```
<slug>-v<version>-<channel>[-<abi>].apk
```

| 字段 | 取值 | 说明 |
|---|---|---|
| `slug` | `beifen-zhong` | 与仓库名一致，玩家能对着仓库找包 |
| `version` | `0.1.0` | 与 `versionName` 逐字一致 |
| `channel` | `release` / `debug` | debug 包带后门口令与 `BuildConfig.DEBUG`，只给自己人 |
| `abi` | 可选 `arm64-v8a` 等 | 第一版不做 ABI 拆分（universal），字段留空 |

例：`beifen-zhong-v0.1.0-release.apk`、`beifen-zhong-v0.1.0-debug.apk`。

不用中文名、不用空格、不用日期串：GitHub Release 的下载链接会被 URL 编码糊成一团，
玩家替我们转述时也会出错。**中文标题放在 Release 正文里，不放在文件名里。**

每个 Release 的正文固定三段：

1. **这版能玩到什么**（章节数、结局数、预计时长）；
2. **已经验过什么**（自动化测试条数 + 真机/模拟器实测项，逐条列）；
3. **已知没验的**（诚实列出，别让玩家替我们发现）。

## 五、签名

- keystore 放仓库外（本作：`../keystore/beifen-zhong-release.jks`），
  路径与口令写进 `android/local.properties`（已 gitignore），构建脚本从那里读。
- **两处异地备份**。keystore 丢了，已装机的玩家就再也收不到覆盖升级——
  只能卸载重装，而对本作来说"卸载"是剧情级的灾难，不只是工程级的。
- `debug` 构建用 Android 默认的 debug keystore，不需要也不应该用发布密钥签。

## 六、发布动作（一次做完的顺序）

```bash
python3 tools/validate_script.py script/act*.json   # 剧本是唯一真相，先验它
cd android && ./gradlew --offline :app:testDebugUnitTest :app:assembleDebug :app:assembleRelease
git add -A && git commit -m "..."                    # 提交（不含 keystore / local.properties）
git tag -a v0.1.0 -m "..." && git push origin main v0.1.0
gh release create v0.1.0 <两个 apk> --title "..." --notes-file docs/release-notes-v0.1.0.md
```

顺序里唯一有代价的是"先测后打 tag"：tag 是对外承诺，承诺不能带编译错误。

发布之后还有一步是**只有发布后能做**的：装一个旧版本号（同签名）的包，在设备上按第八节那条链路
走一遍「检查更新 → 下载 → 安装」，确认它真的能把自己升上来。
这一步没法在发布前验，因为 `releases/latest` 只有发出去才存在。
v0.1.1 已按这条走过一次（含 sha256 校验、挂起态、复用本地包），记录在 `docs/07` 第六节。

## 七、不止一款游戏时先照这张表填

第二款开工前先填这一行，填完的所有名字都从表里推，不要临时起意：

| 字段 | 推法 | 《正在备份》 |
|---|---|---|
| slug | 标题拼音，kebab-case，≤ 20 字符 | `beifen-zhong` |
| 仓库 | `<slug>`，独立 private 仓库 | `cedarln/beifen-zhong` |
| `applicationId` | `cn.linan.<短英文名>`，短名全局唯一 | `cn.linan.backingup` |
| versionCode 起点 | 每款游戏各自从 1 开始，**绝不跨游戏连续编号** | 1 |
| keystore | `../keystore/<slug>-release.jks`，仓库外，一把游戏一把 | `beifen-zhong-release.jks`（DN：`CN=<slug>, OU=games, O=cedarln, L=Wuhan, C=CN`） |
| tag | `v<versionName>` | `v0.1.0` |
| 产物 | `<slug>-v<version>-<channel>.apk` | `beifen-zhong-v0.1.0-release.apk` |
| Release 说明 | `docs/release-notes-v<version>.md` | `docs/release-notes-v0.1.0.md` |

三条硬性约定：

1. **`applicationId` 里不许出现 slug 的拼音**。它是 Android 判断"同一个 App"的唯一依据，
   一旦装机就改不了；`backingup` 这种短英文名可以活过改名，`beifen-zhong` 不行。
2. **一款游戏一个仓库、一把密钥**。真要把两款塞进一个仓库（不建议），
   tag 立刻改成 `<slug>-v<version>`，因为 git tag 里不能有 `/`。
3. **下载页只有一种可安装产物**。同一版本不要再分 `arm64`/`universal` 两个包——
   玩家不会读文件名里的技术字段；要拆 ABIs 等到真的有人抱怨包体太大再说。

## 八、应用内更新：每个 App 都要有，不许跳浏览器

这是 2026-10-28 定下的**跨项目规则**：以后所有 App 都自带「检查更新 → 应用内下载 → 拉起安装」，
不要把玩家丢到浏览器或第三方页面去手动找 APK。理由很实际：跳出去一次，
回来就要重新找包、重新装、还可能被系统的"未知来源"提示劝退——更新率就是这么丢掉的。

统一实现照 `paopao-daily` 的 `UpdateChecker`（零第三方依赖）：

| 环节 | 做法 |
|---|---|
| 查 | `HttpsURLConnection` GET `https://api.github.com/repos/<owner>/<repo>/releases/latest`，匿名可查，**包里不嵌 token** |
| 比 | tag 里提版本号（`v0.1.1` → `0.1.1`），按数字段比，**不做字符串比**（否则 `0.9.0 > 0.10.0`） |
| 下 | 系统 `DownloadManager` 下到 `getExternalFilesDir(null)/update/`，进度在通知栏，自带断点续传；**下完先校验**（大小 + 发布页 asset 的 `digest`），对不上就删掉，不把坏包递到安装器 |
| 装 | `FileProvider`（`${applicationId}.fileprovider` + `res/xml/file_paths.xml`）把 APK 递给系统安装器；Android 8+ 没授权就先跳「安装未知应用」设置页，回来再按一次 |
| 权限 | `INTERNET` + `REQUEST_INSTALL_PACKAGES` |

四条必须一起做到的约束（否则这一节只是把麻烦搬进 App）：

1. **发布页上 `-release.apk` 必须是唯一的正式产物**，且更新器**优先挑名字以 `-release.apk` 结尾的资产**。
   `paopao-daily` 那版是"取第一个 `.apk`"——我们这里同时挂正式包和开发包，
   照抄有 50% 概率把带后门的 `.debug` 包推给玩家。
2. **只在玩家按下按钮时联网**：不做启动时自动检查、不做后台轮询。
   对一个叙事游戏这尤其重要——悄悄联网会把"她只活在本地缓存"这条设定当场戳破。
3. **网络调用关在一个文件里，并用单测守住**。见 `NetworkBoundaryTest`：
   全工程只允许 `update/UpdateChecker.kt` 出现网络 API，且只允许设置页引用它。
   写进注释不算约束，能被测试判失败的才算。
4. **仓库可见性要先想清楚**：匿名查 `releases/latest` 要求仓库公开。
   private 仓库下这个按钮只会得到一个 404。
5. **手机上已经有这一版就别再下一次**：按「下载」先本地核一遍（大小 + sha256），
   过得了就直接给「安装」。11 MB 的重复流量花在玩家身上，等于替我们挨一次"这 App 真傻"。
6. **要能区分"在下载"和"还没开始下"**：`DownloadManager` 只肯在**过了系统校验**的网络上传字节，
   而我们的 `fetchLatest()` 是直连——于是"查得到新版"和"下不动"会同时成立，
   界面停在一个不动的 0%。连门户网络、认证 Wi‑Fi 的玩家看到的就是这个。
   挂起态必须写「等待网络」并说明任务没丢，不许显示百分比（`DownloadProgress.isWaiting`，
   由 `NetworkBoundaryTest` 钉住）。这条在 v0.1.1 是模拟器替真机撞出来的，
   实测记录见 `docs/07` 第六节。
